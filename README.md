# Sellora — AI Revenue Intelligence for B2B Sales

**Find the revenue your sales team is leaving on the table.**

Sellora continuously analyses every opportunity in your pipeline, detects where
revenue is leaking, prices what each leak is costing, ranks opportunities by
expected revenue, and tells the rep exactly what to do next.

The premise: the scarce resource in sales is not email-writing ability, it is
**attention**. Sellora works out where the next hour of selling time creates the
most expected revenue — and always shows its reasoning, so a human can disagree
with it.

It also retains a full outbound stack — prospects, AI-personalized campaigns,
follow-up sequences, and a drag-and-drop CRM board.

Built with **Next.js 15 (App Router) · TypeScript · Tailwind CSS v4 · shadcn/ui ·
Clerk · Prisma · Supabase Postgres · Resend · OpenAI · Vercel**.

## Quick start (zero keys required)

```bash
npm install
npx prisma db push     # creates the local SQLite dev database
npx prisma db seed     # loads the demo workspace (14 prospects, 2 campaigns)
npm run dev
```

Open http://localhost:3000. Sellora works fully with zero keys:

- **Auth** — built-in and keyless. The default sign-in is a **one-time code**
  sent to an email address or phone number (unknown identifiers get a
  workspace automatically); password accounts are supported too
  (scrypt-hashed, database sessions). Without a Resend key — and for SMS,
  until a provider is wired up — codes are shown in the UI in dev mode. The
  sign-in page also offers a one-click **demo workspace** with seed data.
- **AI** — copy is generated by a deterministic local engine until a key is set.
- **Email** — sends are simulated until a Resend key is set.

Add keys to `.env` (see `.env.example`) to progressively enable integrations:

| Key | Enables |
| --- | --- |
| `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` + `CLERK_SECRET_KEY` | Managed authentication via Clerk (SSO, MFA, user management) — replaces the built-in email/password system |
| `OPENAI_API_KEY` | GPT-written personalization, campaign emails, follow-ups, insights |
| `RESEND_API_KEY` (+ `RESEND_FROM_EMAIL`) | Real email delivery |
| `STRIPE_SECRET_KEY` + `STRIPE_WEBHOOK_SECRET` | Real subscription payments via Stripe Checkout — without them, upgrades activate in dev mode (marked "unpaid", no charge) |

Users can also store their own OpenAI/Resend keys per-workspace in
**Settings → API Keys** — those take precedence over the env keys.

## Features

### Revenue Intelligence

- **Overview** — leads with **Revenue at Risk**: the expected revenue currently
  leaking, discounted by likelihood and leak severity. Supporting tiles cover
  recovered revenue, high-intent prospects, deals at risk, overdue follow-ups
  and influenced pipeline. No "emails sent" vanity metric — effort is not an
  outcome.
- **Revenue Leak Feed** — deals losing money for fixable reasons, each stating
  what is happening, why it matters, how much is at stake, and the one action
  to take.
- **Today's Revenue Opportunities** — the answer to *who should I contact
  today?*, ranked by expected value tilted by urgency.
- **Opportunity Score (0–100)** — explainable across five dimensions: customer
  fit, engagement, buying signals, relationship health, deal economics. Every
  point traces to a named rule with a human-readable reason. The score is never
  shown without its reasoning.
- **Recover** — the recovery queue, grouped by leak category (proposal viewed ·
  high intent, no response · meeting with no next step · needs follow-up ·
  going cold · previously lost, new signal) and sorted by expected recoverable
  revenue.
- **Next Best Action** — exactly one recommended action per opportunity, with
  the evidence behind it. "Wait" is a real recommendation, not a fallback.
- **Signals** — every detected buying signal, chronological, with behavioural
  signals (what the buyer did) distinguished from firmographic ones (what
  happened to the company).
- **Impact** — revenue recovered, pipeline influenced, opportunities saved,
  meetings generated, and a full attribution log. Every figure is written when
  a human acts on a recommendation, never inferred at read time.

### Outbound

- **Dashboard** — total prospects, emails sent, reply rate, meetings booked,
  AI performance score, 30-day outreach chart, pipeline distribution, activity feed.
- **Prospects** — full CRUD with search + status/industry filters. Each prospect
  gets a one-click AI kit: company summary, icebreaker, outreach angle, cold
  email, LinkedIn message — all editable before anything sends.
- **Campaigns** — create a campaign (audience, goal, tone), add prospects,
  generate AI emails per recipient (individually or in bulk), send via Resend,
  and track Draft → Sent → Opened → Replied.
- **AI follow-ups** — 3-step sequences with escalating tones (friendly bump,
  direct question, witty breakup), each with its own CTA strategy. Sequences
  stop automatically when a prospect replies.
- **Pipeline** — drag-and-drop kanban across New Lead → Contacted → Interested →
  Meeting → Proposal → Won/Lost, with activity logging on every stage change.
- **AI Insights** — GPT-generated recommendations computed from your live
  outreach data (hottest prospects, stale threads needing a follow-up,
  week-over-week reply-rate movements, best-performing campaign).
- **Settings** — profile, company/sender identity (used in AI prompts and the
  email `From:`), API keys.
- **Billing** — real subscriptions (Free / Pro $19.99 / Max $39.99, monthly or
  yearly) with Stripe Checkout, webhook-synced state, cancel-at-period-end,
  live usage meters, and plan limits enforced on prospects, campaigns, and
  monthly email volume. First-time OTP users get a one-step onboarding
  (name + workspace).

## Architecture

```
app/
  (marketing)/        Landing page, sign-in, sign-up
  (app)/              Protected product (dashboard, prospects, campaigns,
                      pipeline, insights, settings) — server components +
                      server actions per module (actions.ts)
components/
  ui/                 shadcn/ui primitives
  marketing/ app/ dashboard/ prospects/ campaigns/ pipeline/ insights/ settings/
lib/
  revenue/            Revenue Intelligence layer
    config.ts         Every tunable number: scoring weights, stage win-rate
                      baselines, leak thresholds. Versioned.
    opportunity-score.ts  Pure 5-dimension explainable scorer (no AI, no DB)
    leaks.ts          Pure leak detection + revenue-at-risk pricing
    next-action.ts    Pure next-best-action engine (returns exactly one)
    money.ts          Expected revenue = value × probability, formatting
    opportunities.ts  Server-side scoring pipeline + snapshot persistence
    queries.ts        Read models for every revenue screen (batched)
    recommendations.ts  Recommendation ledger + revenue attribution
  auth.ts             Session resolution + workspace provisioning (Clerk or built-in)
  local-auth.ts       Built-in auth: database sessions + HTTP-only cookie
  password.ts         scrypt password hashing
  ai.ts               OpenAI wrapper with local fallback for every generator
  email.ts            Resend wrapper with simulated-send fallback
  db.ts               Prisma client singleton
  metrics.ts          Dashboard aggregates
  insights.ts         Insight context builder
  validators.ts       Zod schemas shared by forms and actions
prisma/
  schema.prisma       Organizations, Users, Settings, Prospects, Campaigns,
                      Emails, FollowUps, Activities, Insights,
                      Opportunities, OpportunityScoreSnapshots (+Factors),
                      BuyingSignals, Recommendations, RevenueAttributions
  seed.ts             Demo workspace (one scenario per leak category)
```

### How the revenue layer is put together

**Scoring is pure and explainable.** `opportunity-score.ts`, `leaks.ts` and
`next-action.ts` have no AI, no database access and no clock except an
injectable `now`. Every number traces to a rule a human can read, which is why
the UI can always show its work. AI never produces a score — at most it
narrates one afterwards.

**Scores are snapshots, never overwrites.** Each run writes an
`OpportunityScoreSnapshot` plus one `OpportunityScoreFactor` row per rule that
fired, stamped with the config version. Past scores stay auditable after the
model is retuned.

**Leaks are computed live; recommendations are persisted.** A leak is a
*current state* ("no follow-up for 4 days"), so storing it would need a cron job
to stay true — and a stale leak table is worse than none, since it would tell a
rep to chase a deal they closed yesterday. A recommendation is a *decision*, so
it is written down: what Sellora suggested → what the rep did → what happened.

**Revenue at risk is deliberately conservative.** It is deal value × win
probability × a severity discount, not the full deal value. Inflating the
headline number would destroy its credibility the first time a VP checked it
against their CRM.

**Attribution is only ever written on a real user action.** The Impact page
reports facts, never estimates. If nobody works a recommendation, it honestly
reports zero.

**All behavioural evidence flows through `BuyingSignal`.** Pricing-page visits,
proposal opens and meetings are signals, not bespoke columns — so a future
Gmail or HubSpot connector only has to write signals, and every downstream
score, leak and recommendation updates itself.

### What is *not* built

Per the brief's own warning — do not claim the AI improves itself unless the
learning system exists — this is Phase 1 only:

- **Nothing learns automatically.** Scoring weights in `lib/revenue/config.ts`
  are hand-tuned and static. The `Recommendation` ledger records the data an
  outcome-based learner would need; it does not train anything.
- **Win-probability baselines are conventional industry figures**, not learned
  from your workspace's history. The UI labels them as estimates.
- **No live integrations yet.** Signals arrive by CSV, manual entry, or the demo
  provider. Gmail, CRM sync and website tracking are Phase 2; anything from the
  demo provider is labelled "demo data" everywhere it appears.

Design decisions worth knowing:

- **Multi-tenancy** — every row hangs off an `Organization`; all queries and
  server actions are scoped by `orgId` derived from the session, never from
  client input.
- **Server actions over API routes** — mutations live in per-module
  `actions.ts` files with Zod validation and a uniform `ActionResult` shape;
  pages are server components reading Prisma directly.
- **Graceful degradation** — AI and email calls fall back to local
  implementations rather than erroring, so a missing/expired key never bricks
  the product. Toasts tell the user which engine produced the result.
- **Portable schema** — status/stage columns are typed string unions validated
  with Zod (identical behavior on SQLite and Postgres).

## Deploying (Vercel + Supabase)

1. **Database** — create a Supabase project. In `prisma/schema.prisma`, change
   the datasource provider from `sqlite` to `postgresql`. Set `DATABASE_URL` to
   the transaction-pooler string (port 6543, `?pgbouncer=true`) and run
   `npx prisma db push` (or generate and commit a migration) against the
   session pooler / direct string once.
2. **Clerk** — create an application, copy both keys into Vercel env vars.
3. **Resend** — verify your sending domain, create an API key, set
   `RESEND_FROM_EMAIL` to a verified address.
4. **OpenAI** — create an API key (`OPENAI_MODEL` overrides the default
   `gpt-4o-mini`).
5. **Vercel** — import the repo, set the env vars from `.env.example`, deploy.
   `postinstall` runs `prisma generate` automatically.
